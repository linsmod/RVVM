## 现状：fork 被整个委托给了 host

```3374:3433:src/core/rvvm_user.c
// long sys_clone(unsigned long flags, void *stack, ...);
static int rvvm_sys_clone(...)
{
    if ((flags & UAPI_CLONE_VM) && !(flags & UAPI_CLONE_VFORK)) {
        ...                       // guest 线程 = host 线程
    } else {
        // Emulate vfork via fork too
        return fork();            // guest 进程 = host 进程
    }
}
```

`fork()` 在这里 fork 的是**模拟器自己**。它在 Linux 上"意外能用"，是一串巧合凑齐的：

- guest 内存就是模拟器自己的堆缓冲（1 GiB 平铺，`rvvm.c:1102-1125`），host fork 的 COW 恰好等价于 guest 内存写时复制；
- guest fd 就是 host fd（**没有 fd 表**，`sys_open` 直接返回 `open()`），host fork 自动复制 fd 表、共享 file description、保留 CLOEXEC；
- `wait4` 直接转发 host `wait4`（`5254-5264`），父 guest 能 reap 子 host 进程并拿到退出码；
- `execve` 用 `execve("/proc/self/exe", {"-user", path, ...})` 重入自己（`5192-5204`）。

于是 fork→exec→wait 整条链都落在了 host 内核上。

## 为什么必须换掉

1. **Win32 没有 fork**：`posix_shim.c:312` 就是 `errno = ENOSYS`，`execve` 也没有真实实现（无 `/proc/self/exe`）。README 的 "fork/wait4: no process model on Windows" 指的就是这个。
2. **Android 上更糟**：fork 出来的是宿主 app 进程——带 JNI 线程池、Surface、GL/音频设备，且 `exit_callback` 会被子进程继承，子 guest 一退出就会在副本里触发宿主的 run 收尾。
3. **即使在 Linux 上也只是巧合**：`rvvm_userland_t`（`698-814`）被整块复制，里面正被别的（没被 fork 的）线程持有的自旋锁在子进程里永久锁死；TTY session / GL context / WASAPI 流 / 窗口 / cmdpost 回调全部变成两份、且都以为自己拥有；`getpid/gettid` 直接返回 host pid/tid（`3756`、`5006`），`kill` 只能在"信号号 < 64"时就地拦截（`4791-4804`）。

结论：fork 不能委托 host。**"guest 进程"必须是模拟器自己的对象**——而这套代码已经具备跑多个实例的能力（`rvvm_user_create()`，Android host 的 multi-task 就在用），fork 正是它的自然延伸。

## 要复制的其实是三件独立的事

| 复制对象 | 现在靠 | 自己做需要 |
|---|---|---|
| 地址空间 | host fork 的 COW | 复制 guest RAM（1 GiB 平铺，**host COW 用不上**） |
| fd 表 | host fork 复制 host fd 表 | 需要一张 guest fd 表（现在完全没有） |
| pid / 父子 / 退出码 | host wait4 | 需要模拟器自己的进程表 + wait 队列 |
| 只有调用线程存活 | host fork 天然如此 | 线程注册表按进程切分 |

**内存**是最先要想清楚的：guest RAM 是 `vma_alloc` 的平铺缓冲，模拟器内部做页级 COW 没有便宜的实现点——地址翻译会把 host 指针缓存进 TLB（`riscv_mmu.c:145`、`riscv_mmu.h:157-166`），JIT 更是直接对 host 指针发写指令，没有地方塞"写保护"检查。

现实做法是**只复制已映射区域**，而不是整块 1 GiB：

- ELF 段 + brk：`[GUEST_DYN_BASE, guest_brk_ptr)`（`623`、`737-743`）
- 栈：只复制 `[sp, stack_top)` 再向上取整，而非整个 64 MiB（`1940-1941`）
- mmap 区：分配器目前只记空闲洞（`guest_free`，`2011-2036`），要补一张"存活映射表"

对 busybox 这种规模约每 fork 几 MiB，可接受；全量 1 GiB memcpy 则不可接受（20 次 fork = 秒级卡顿）。

**fd 表**是第二块地基，也是 exec（CLOEXEC）的前提。省事版是保持 guest fd == host fd、fork 时枚举 `/proc/self/fd`（win32 用 `_get_osfhandle`）逐个 dup；正路是加 `guest fd → {host fd, cloexec, dup/close ops}` 表，好处是 win32 的 socket dup 能走 `win_socket`，asset 的合成 fd 也天然归位，热路径只多一次数组索引。

## 落到本仓库的接缝

1. **把 `rvvm_user_linux_ex()` 里"在 machine 上引导一个镜像"抽成 `guest_spawn(ctx, path, argv, envp)`**（`5772` 起的这段：ELF 加载、`stack_put_*` `5542+`、`jump_start()` `5462`）。它本来就是"一台 machine 连着跑好几个 guest"（`5787-5793` 的注释就是在清上一次的残留）。抽出来之后 `execve` 不再需要 `/proc/self/exe`，**这一条单独就能修好 win32/Android 的 exec**。
2. **加进程表**：`rvvm_process_t { pid, ppid, exit_status, children }`，`wait4` 改为在模拟器自己的子进程队列上等（condvar/event + WNOHANG 超时），`exit_group` 置状态唤醒父进程，`getpid/getppid` 返回仿真 pid。这一步也是 win32 上 `wait4` 有定义的前提。
3. **加 fd 表**，把 `sys_open/dup/dup2/close` 先搬过去，`execve` 时按 CLOEXEC 清理。
4. **实现 in-process fork**：新建 machine（新 hart 集合、新 JIT 上下文——JIT 缓存 host 指针，绝不能继承）、复制已映射区域、dup fd 表、复制调用线程寄存器（`X0-X31`/`F0-F31`/PC/SP/TLS，a0=0）后起线程。`vfork` 同一条路，父线程 park 到子进程 exec/exit。
5. **必须明确的策略**（不明确就一定出 bug）：子进程不继承 TTY session、GL/EGL context、窗口、音频流、sensor 队列、`host_ctx`/cmdpost；`exit_callback` 只由宿主最初启动的那个进程触发，子进程退出只回报给父进程；多线程 guest 里 fork 只保留调用线程。

## 这一步做了什么：guest 进程成为模拟器自己的对象

**1. 进程注册表**（`rvvm_process_t` + `ctx->procs`）
每条记录：`pid / ppid / host_pid / run_root / exited / exit_status / exit_event`，带引用计数——因为父进程可能在子进程线程还在收尾时就 reap 它。`host_pid` 区分“由独立宿主进程跑”（今天 Linux 上 fork 的做法）与“在本地址空间里跑”（第 4 步 in-process fork 的形态），所以 wait4 两种都能处理，且第 4 步不需要推翻它。

**2. guest 的 pid/tid 空间**
pid 和 tid 用同一个计数器（同 Linux，两者不冲突）；根进程从 100 起步、ppid 报 1——避免 guest 把自己当 init（`getpid()==1` 会改变程序的信号行为）。主线程 `tid == pid`，所以 `getpid()==gettid()` 这个惯用法成立。实测：`pid=100 ppid=1`，execve 之后 **pid 不变**（进程身份延续），新线程是 `pid=100 tid=101`。

**3. wait4 由注册表驱动**
过滤器在本地方析（guest pid **绝不**透传给宿主）；宿主进程承载的子进程 → 宿主 `wait4(host_pid)` 双向翻译，保住了 Linux 上现在就能用的 fork+wait；本地址空间内的子进程 → 在其 exit_event 上等，带界的轮询 + 重新扫描（事件是一次性的，这样另一个等待者抢走唤醒也不会挂死）。支持 WNOHANG、ECHILD，以及**挂起信号/stop 请求会打断等待**（否则一个正在等子进程的 shell 对 ^C 就是聋的）。

**4. “guest 进程退出”与“run 结束”拆开**
状态先写进注册表再收尾（等着的父进程靠它醒来）；`run_root` 决定是否触发宿主回调/`_Exit`。这是第 4 步能正确工作的前提——子进程退出不能把宿主的 run 收掉。

**5. kill/tkill/tgkill 必须跟着改（这是这一步里最关键的安全点）**
pid 一旦变成仿真的，原实现里“未知信号号 → 转发宿主 `kill(guest_pid, sig)`”就会把信号发给**无关的宿主进程**。现在 pid 一律先在注册表校验（不存在 → ESRCH），宿主转发只针对我们自己 fork 出来的 host_pid；顺带 `tkill/tgkill` 在 Windows 上也可用了（原先直接 ENOSYS）。

**顺手修掉的两个真 bug**
- `CLONE_CHILD_SETTID` 竞态：父进程在 spawn **之后**才写该字段，而子线程第一条指令就读它 → 写入可能丢失。现在两个 tid 字段都在线程运行前写好。
- fork 的子进程：原样继承父进程的进程树和线程注册表（描述的是父进程的线程），run 收尾会白等 1 秒“永远不会注销的线程”。现在子进程重建线程表（只留调用线程）、重置进程树和锁、tid=pid。

## 做了什么：guest 描述符表

**结构上**：`rvvm_process_t` 持有 `rvvm_fd_entry_t fds[]`，每槽 = `{宿主 fd, FD_CLOEXEC}`。

关键取舍：**共享“打开文件描述”这件事交给宿主**——`dup(2)` 让宿主任命一个新 fd 指向同一描述，偏移和状态自然共享，模拟器不需要建模。表只承载宿主做不到的部分：进程持有哪些槽、exec 关哪些、以及（第 4 步）guest fd 到底对应哪个宿主 fd——同一宿主进程里两个 guest 进程不可能同时拥有宿主 fd 1。

我第一版写成了「引用计数的共享描述对象」，**是错的**：identity 映射下每个槽就是各自的宿主 fd。测试把它抓出来了（见下）。

**接入的调用点**（产生 fd 的全部）：`openat / pipe2 / dup / dup3 / fcntl(F_DUPFD、F_DUPFD_CLOEXEC) / socket / socketpair / accept / accept4 / eventfd2 / epoll_create1 / memfd_create`。asset 挂载的描述符不进表（它有自己那套 run 结束扫描）。

**三个语义**：
- `close(2)` 先问表；未跟踪的落回宿主 close（保留 EBADF 等错误报告）。
- **FD_CLOEXEC 归表**：`F_GETFD/F_SETFD` 由表作答（*只*在已跟踪时拦截——未跟踪的必须走到宿主，否则被 exec 关掉的 fd 会被误报为成功，这点测试也抓到了）；`execve` 关闭被标记的槽。这是 O_CLOEXEC 唯一能被落实的地方，因为宿主 open flags 根本不翻译它。
- 进程销毁时它的描述符随之关闭（顺带把上一次 run 残留的 fd 收回来——以前是漏的）。宿主 fork 的子进程放弃继承的记账（共享宿主 fd 表时两侧无法各自计数）。

## 测试暴露出的两个真宿主 bug（已在 posix_shim 修掉）

1. **`dup2` 返回值**：Windows `_dup2` 成功返回 **0**，而 POSIX 返回 newfd。所以 guest 的 `dup2(fd, 30)` 拿到 0 而不是 30——在它自己的视角里等于改写了 fd 0。这是既有 bug，我的测试直接撞上了。顺带把 `oldfd == newfd` 收紧为校验 oldfd（无效则 EBADF）。
2. **`fcntl(F_GETFD/F_SETFD)` 无条件返回 0**，连已关闭的 fd 都报成功——让“exec 关掉了它”无从验证。现已校验 fd 有效性。

## 做了什么：in-process fork

**子进程 = 同一宿主进程里的新 machine**。宿主进程完全不动——这正是意义所在：Windows/Android 没有 fork 也能用，guest fork 不再复制窗口/音频流/整个 Android app。

- **内存**：子进程拿全新缓冲，按已知跨度拷贝——镜像+brk `[image, brk)`、mmap 区 `[GUEST_MMAP_BASE, bump)`（空洞清零回去，guest munmap 过的子进程要读到新页）、栈 `[sp, stack_top)`。busybox 量级几 MiB，不是整块 1 GiB。**JIT 缓存宿主指针，所以内存绝不能共享**——这也是为什么必须拷贝而不是映射。
- **上下文继承**（fork 该带的）：文件系统视图（prefix/cwd/asset 挂载）、凭据、信号处置、控制台输出 sink（io callback）、分配器与堆状态。**不带**的：宿主的 run（子进程没有 exit callback）、窗口/音频桥、控制台 session、挂起信号。
- **进程记录跨侧共享**：一条记录同时挂在父、子两个注册表里——子进程在自己的 ctx 上标记退出，父进程的 wait4 读到的是同一个对象。`run_root=false` 保证子进程退出不会收掉宿主的 run。
- **寄存器**：全量复制，落在 ecall 之后，a0=0；子进程主线程 `tid = pid`。
- **vfork**：同一实现 + 父线程 park 到子进程 exec 或退出（`vfork_done` 标志，exec 与退出都会置位并唤醒）。子进程有自己的内存副本，所以 park 是保序而非保安全。

**fd 表在此处暴露出设计修正**：表原本挂在进程记录上，而记录是父子共享的——那样父子会共用同一张表。表必须随**地址空间**（ctx）走，已迁移；子进程继承父进程的槽位并标记 `shared`（子进程永不 host-close，否则会拿走父进程的描述符）。

## 做了什么

**1. guest fd 与 host fd 解耦**（表的核心语义变化）
- 新增 `userland_fd_install(guest, host, flags)` / `userland_fd_slot_alloc(min)` / `userland_fd_host(fd)`：槽位号是 guest 的编号，`entry.fd` 是宿主编号，两者不再恒等。
- **fork 继承改为 `dup()`**：子进程拿到自己的宿主描述符，共享同一个 open file description（偏移共享、管道对端仍是同一根），但各自 close 互不影响——这正是 step 4 里"子进程 dup2 会改写父进程 fd 1"的根因。宿主 dup 不出来时（描述符耗尽）才回落到旧的 shared 共享模式。
- **dup/dup3/F_DUPFD 改为表内分配**：不再用宿主 `dup2` 去占宿主编号。`dup2` 返回 guest 指定的 newfd，`dup` 返回表内最低空槽。

**2. 全量消费点接翻译层**：read/write/readv/writev/pread/pwrite/lseek/fstat/getdents/ioctl/flock/ftruncate/fchown/fchmod/fstatfs/fchdir/fallocate/mmap 的 fd、以及 `*at` 家族的 dirfd（mknod/mkdir/unlink/symlink/link/faccessat/fchmodat/fchownat/openat/newfstatat/readlinkat/renameat2/statx/faccessat2）、socket 家族、epoll、sendmmsg。

**3. 控制台判定修正**（重定向能工作的前提）：fd 0/1/2 只有**未被表跟踪**时才是控制台。`cmd < file` 后 fd 0 走真实文件、`cmd > file` 后 fd 1 归重定向目标，`io_callback` 改收宿主 fd。否则管道里的字节会被送进 logcat/TTY。

**4. 0/1/2 预留**：表初始化时把控制台标为"已占用但不属于表"。这是测试抓出来的——否则 `dup()` 会返回 0（表以为 0 空闲）。启动路径上 `userland_fd_table_free` 会在新 run 时清掉预留，已改为 free 后重新 init。

**5. select/poll 真正做集合转换 + 翻译**：顺带修了 Windows 的既有问题——宿主 `fd_set` 是"数字列表"而 guest 是位掩码，原来直接把 guest 指针传给 `select()` 在 Windows 上是错读的。

**6. sendfile (syscall 71)**：之前误判为 readv（readv=65 早已有实现），71 其实是 `sendfile`，busybox `cat` 走的正是它。实现为带 bounce buffer 的读取-写出循环，保留语义：显式 offset 时不移动文件位置、短拷贝返回计数、EOF 返回 0。
